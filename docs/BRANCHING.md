# 分支与发布约定

## 三个明确入口

| 入口 | 含义 |
| --- | --- |
| `master` | 唯一长期维护的主分支，与 GitHub 默认分支一致 |
| `codex/<任务>` | 短期开发分支；一个任务对应一个 PR，通过检查后 Squash 合并 |
| `v2.0.0` 等标签 | 不移动的正式版本快照，对应 GitHub Release |

本地服务目录保持在 `master`。开发使用独立工作目录，避免把未验收代码直接载入正在运行的服务。不再新建常驻 `dev`、`release` 或重复备份分支。

## 清理规则

- 清理前刷新远端引用，检查 PR 的合并状态、最终提交、工作目录和未提交文件。
- Squash 后，Git 可能显示旧分支“未合并”。必须同时核对 GitHub 合并记录与代码差异，不能只看提交数量。
- 只清理已确认完成且工作目录干净的任务分支。未合并修复、独有提交、脏目录和仍在使用的目录保留，并标明用途。
- 删除引用前在仓库外保存可校验的 Git bundle 和分支清单；有未提交文件的目录不得当作可回收项。
- 不批量合并历史 PR。依赖升级单独评估与测试，不作为界面或文档发布的附带变更。

## 发布顺序

1. 在任务分支完成实现、文档、截图和版本信息。
2. 运行后端测试、前端单测、构建及相关浏览器测试；检查 diff 与敏感数据。
3. Push 并创建 PR；等待最终提交的 CI 和阻塞性审查完成。
4. 合并后快进本地主分支，备份并更新原有服务，检查真实接口版本、资源与交互。
5. 在已验收的合并提交创建版本标签和 GitHub Release，再清理本次完成的分支。

后端产品版本定义在 `app/version.py`；前端 `package.json` / `package-lock.json`、启动横幅、Changelog 与 Release 保持一致。内部 API / 数据库版本不随产品版本机械替换。
